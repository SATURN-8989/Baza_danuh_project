# Этап 2. Концептуальное проектирование — решение кейса «Учёт в музыкальной школе»

## 1. ER-диаграмма (нотация Чена)

Модель построена строго по итогам этапа 1: **6 сущностей** (`Пользователь`, `Преподаватель`, `Класс`, `Урок (Расписание)`, `Журнал_занятий`, `Платёж`). Ключи и атрибуты совпадают со сводной таблицей этапа 1. Модель не зависит от конкретной СУБД: здесь нет типов данных, индексов и партиций.

![ER-диаграмма (нотация Чена)](<./screens/ER-диаграмма (нотация Чена).png>)

### Легенда обозначений (нотация Чена)
* **Прямоугольник** — сильная сущность; **двойной прямоугольник** — слабая сущность (`Журнал_занятий`).
* **Овал** — атрибут; **подчёркнутый текст** — ключевой атрибут; **пунктирное подчёркивание** — частичный ключ слабой сущности.
* **Ромб** — связь; **двойной ромб** — идентифицирующая связь.
* **1 / M** у линий — кардинальность; **двойная линия** — обязательное участие (полное включение).

### Сущности и атрибуты

| Сущность | Тип | Атрибуты (ключевые — подчёркнуты) |
| :--- | :--- | :--- |
| **Пользователь** | Сильная | <u>ID_пользователя</u>, Фамилия, Имя, Отчество, Телефон, Email, Дата_регистрации, Текущий_баланс |
| **Преподаватель** | Сильная | <u>ID_преподавателя</u>, ФИО, Телефон, Специализация |
| **Класс** | Сильная | <u>ID_класса</u>, Номер_кабинета, Вместимость |
| **Урок (Расписание)** | Сильная | <u>ID_урока</u>, Дата_проведения, Время_начала |
| **Журнал_занятий** | Слабая (двойной прямоугольник) | <u>ID_записи</u> (частичный ключ), Статус_явки, Домашнее_задание |
| **Платёж** | Сильная | <u>ID_платежа</u>, Сумма_оплаты, Дата_времени |

### Примечания к диаграмме
* Поля-ссылки из этапа 1 (`ID_преподавателя`, `ID_пользователя`, `ID_класса` в расписании и др.) на ER-диаграмме **не рисуются овалами**, а выражаются через связи-ромбы.
* Сущность **«Урок (Расписание)»** выделена как самостоятельная сильная сущность, так как она связывает сразу трёх участников процесса (пользователя, преподавателя и класс).

## 2. Описание связей

| Связь | Сущности | Тип | Смысл | Обоснование типа |
| :--- | :--- | :--- | :--- | :--- |
| **посещает** | Пользователь — Урок | `1:M` | Один пользователь посещает много уроков; каждый индивидуальный урок привязан к одному пользователю | Ученик занимается регулярно; каждый урок в сетке — отдельная запись (процесс «Назначение расписания») |
| **ведёт** | Преподаватель — Урок | `1:M` | Преподаватель ведёт много уроков; каждый урок проводит один преподаватель | Поле преподавателя обязательно: у каждого занятия есть ведущий педагог |
| **проходит в** | Класс — Урок | `1:M` | В одном классе проходит много уроков (в разное время); каждый урок проходит в одном классе | Структурное ограничение: занятие не может проходить без кабинета |
| **фиксируется в** | Урок — Журнал_занятий | `1:M` (идентифицирующая, двойной ромб) | По уроку создаётся запись в журнале; каждая запись относится ровно к одному уроку | Структурное ограничение: отметка о явке и ДЗ не существуют без самого урока |
| **вносит** | Пользователь — Платёж | `1:M` | Один пользователь вносит много платежей за всё время; каждый платёж принадлежит одному пользователю | Ученик/родитель регулярно пополняет баланс (процесс «Оплаты») |

> Бизнес-правила Б1 и Б2 (запрет накладок времени у преподавателя и класса) являются ограничениями состояния и проверяются логикой/триггерами, поэтому не меняют кардинальность связей `1:M`.

## 3. Слабые сущности

| Сущность | От чего зависит | Почему слабая | Ключ |
| :--- | :--- | :--- | :--- |
| **Журнал_занятий** | Урок (связь «фиксируется в», двойной ромб) | Факт посещения и домашнее задание имеют смысл только в контексте конкретного состоявшегося урока из расписания (структурное ограничение этапа 1) | Составной: `ID_урока` (ключ родителя) + `ID_записи` (частичный ключ) |

---

## 4. Атрибуты связей (обоснование сущности «Урок»)

Сущность **«Урок (Расписание)»** оформлена как полноценная сущность, а не как связь с атрибутами. 
* **Причина:** у урока есть обязательные ссылки сразу на **трёх** участников (`Пользователь`, `Преподаватель`, `Класс`), собственный уникальный ключ (`ID_урока`) и дочерняя слабая сущность (`Журнал_занятий`). В нотации Чена ромб не может иметь первичный ключ и связываться с третьими сущностями.

| Атрибут (из этапа 1) | Где хранится | Почему не на связи |
| :--- | :--- | :--- |
| **Дата_проведения** | Урок (Расписание) | Свойство конкретного запланированного занятия в сетке |
| **Время_начала** | Урок (Расписание) | Определяет точный слот занятия для проверки конфликтов (Б1, Б2) |
| **Статус_явки** | Журнал_занятий | Фиксируется по факту проведения урока (процесс «Фиксация посещаемости») |
| **Домашнее_задание** | Журнал_занятий | Привязано к конкретному прошедшему занятию |

---

## 5. Замечания о связях M:N

Исходное отношение **«Пользователь занимается у Преподавателя»** является связью **многие-ко-многим (`M:N`)**: один ученик может заниматься у разных преподавателей (например, вокал и фортепиано), а один преподаватель обучает множество учеников. В реляционной БД прямых связей `M:N` нет, поэтому она заменена сущностью **«Урок (Расписание)»**.

| Исходная M:N | Чем заменена | Преобразование на этапе 3 |
| :--- | :--- | :--- |
| **Пользователь — Преподаватель** (занимается у) | Пользователь — Урок (`1:M`) + Преподаватель — Урок (`1:M`) | Внешние ключи `FK_Пользователь` и `FK_Преподаватель` (а также `FK_Класс`) в таблице `Расписание` |
